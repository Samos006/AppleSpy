# AppleSpy

Телеграм-бот и мини-апп для слежения за ценой и наличием товаров
в Золотом Яблоке.

Бот: [@AppleSpyBot](https://t.me/AppleSpyBot) · Мини-апп: https://applespy.panoff.dev

Бот намеренно минимален: он принимает ссылку на товар и присылает уведомление
об изменении с двумя кнопками — «Открыть в приложении» и «Открыть в ЗЯ».
Всё остальное (графики, история, настройки, целевая цена) живёт в мини-аппе.

## Как устроена добыча данных из ЗЯ

Это самая нетривиальная часть проекта, и почти всё здесь выяснено опытным
путём. Если будете дорабатывать — прочитайте, это сэкономит часы.

### Эндпоинт

```
GET https://goldapple.ru/front/api/catalog/product-card/base/v3
    ?locale=ru&cityId=<guid>&regionId=<guid>&itemId=<id>
```

`itemId` — первое число в адресе товара:
`goldapple.ru/`**`19000116114`**`-resveratrol-...`

Старый `POST /front/api/catalog/product-card` **больше не существует** и отдаёт
404 — в старых статьях по парсингу ЗЯ он ещё встречается.

Цена лежит в `data.variants[].price.actual` (плюс `regular` и `old`), наличие —
в `data.variants[].inStock`. Ссылка на картинку приходит **шаблоном**
с плейсхолдерами `${screen}` и `${format}` — без подстановки она нерабочая.

### Защита

Сайт закрыт связкой Variti + FACCT (ex-Group-IB):

1. Первый заход отдаёт HTML-заглушку `Gold Apple — checking device`.
   JS считает отпечаток устройства и получает клиренс-куку `cfidsw-goldapple`.
   До этого весь `/front/api/catalog/*` отвечает 403.
2. Трафик из хостинг- и VPN-подсетей может получить страницу
   «Доступ к сайту временно ограничен владельцем» — так, например, наглухо
   отсекается HOSTKEY.

### Грабли, на которые мы наступили

**Блокировка приходит с кодом HTTP 200.** Наивный парсер увидит «успех»
и сохранит мусор. Поэтому заглушки распознаются по телу ответа
(`classify_block` в [fetcher.py](backend/app/goldapple/fetcher.py)), а не по
статусу.

**Заглушка 403 «An error occurred» — это не блок по ASN.** Она означает всего
лишь отсутствие клиренс-кук. Если свалить их в одну кучу, диагностика начнёт
уверенно врать про блокировку сети там, где её нет.

**User-Agent обязан соответствовать реальной платформе.** Это главная засада.
С `Windows`-UA на Linux-сервере device-check не проходит **никогда** — заглушка
висит вечно. С `Linux`-UA на той же машине проверка проходит за 4 секунды.
FACCT сверяет заявленную платформу с фактической. Отсюда
[fingerprint.py](backend/app/goldapple/fingerprint.py): UA берётся от `sys.platform`,
и один и тот же набор заголовков используется и браузером, и HTTP-клиентом.

**Ждать куку `ga-device-id` бесполезно** — её ставит само приложение ЗЯ уже
после проверки. Единственный честный признак успеха — отдаёт ли API карточку.

**Вкладку после проверки трогать нельзя.** Пробовали уходить на лёгкую
страницу того же домена и обрывать догрузку приложения фильтром — оба приёма
экономят трафик и оба ломают клиренс: следующий запрос получает 403.

**`regionId` не всегда равен `cityId`.** У Москвы город и регион — один и тот
же GUID, у Тюмени регион отдельный (Тюменская область). Пару надо задавать
согласованно, иначе ЗЯ подбирает магазин сам.

**`inStock` у ЗЯ дрожит, и это не лечится запросом.** Самая неприятная находка.
При неизменной цене наличие переключается туда-обратно: за сутки один товар
дал шесть переключений 2950 ₽ «есть → нет → есть». Проверено, что это **не наша
ошибка**: внутри одной браузерной сессии значение стабильно (8 замеров подряд
в одной сессии — одинаковы), скачки происходят между сессиями, при одном и том
же `client-store-code: default` и правильной паре город/регион. То есть
источник отдаёт разное в зависимости от того, какой склад ответил.

Лечится только на нашей стороне — подтверждениями, см. `confirm_stock`
в [checker.py](backend/app/services/checker.py): новое значение наличия
принимается лишь после `STOCK_CONFIRMATIONS` совпадений подряд. На реальной
последовательности дрожания это превращает 6 переключений в 1. Плюс страховка
`NOTIFY_COOLDOWN`: одинаковое событие по товару не уходит пользователю чаще
раза в 6 часов.

Цены подтверждений не требуют — они не дрожат, и задержка тут не нужна.

Закреплять локацию через `POST /front/api/location/address` не нужно: этот
вызов работает (возвращает имя города, чем удобно проверять GUID), но
**сбрасывает клиренс** — следующий запрос карточки получает 403. Достаточно
правильной пары параметров в запросе.

**Один успешный ответ ещё не означает, что сессия готова.** Сразу после
проверки страница перезагружается, и запрос, посланный в это окно, получает
403 — при том что предыдущий, секундой раньше, вернул 200. Поэтому сессия
считается устоявшейся только после двух успешных ответов подряд с паузой,
а первый 403 в бою не хоронит сессию: он прощается, и запрос повторяется.

**С резидентного и с датацентрового адреса поведение разное:**

| Откуда | device-check | Переносятся ли куки в httpx |
|---|---|---|
| Резидентный РФ (Ростелеком и т.п.) | проходит | **да** — опрос дёшев |
| Датацентр (наш сервер, DK) | проходит | **нет**, 403 при любых заголовках |
| Датацентр РФ (HOSTKEY) | не доходит | блок по ASN |

С датацентрового адреса клиренс привязан не только к кукам, но и к самому
клиенту (видимо, к TLS-отпечатку): ни набор заголовков, ни отключение HTTP/2
положения не меняют.

### Отсюда два режима работы

Режим выбирается автоматически по наличию `GA_PROXIES`.

**Без прокси (текущий режим).** Все запросы идут внутри вкладки, прошедшей
проверку — [session.py](backend/app/goldapple/session.py). Одна проверка
(~10 c) обслуживает целый час опроса, каждая последующая карточка забирается
за 0,2–1 c. Успешность на замерах — 7 из 8. Трафик сервера не тарифицируется,
поэтому загрузка приложения внутри вкладки роли не играет.

**С прокси.** Если в `GA_PROXIES` заданы **резидентные или мобильные РФ**
прокси, браузер один раз проходит проверку, а дальше работает дешёвый httpx
с полученными куками — быстрее и легче по памяти. Датацентровые прокси
(в том числе «индивидуальные IPv4» у любого провайдера) не подходят.

Про ротацию: нужна **липкая сессия**. Клиренс привязан к IP, поэтому смена
адреса на каждом запросе означает новую проверку каждый раз. У поставщиков
вроде proxy.market каждый порт даёт отдельную сессию — можно перечислить
несколько портов через запятую, `ProxyPool` ротирует их сам и выводит
сбойные из оборота.

### Проверка доступа

```bash
cd /home/admin/applespy && ./venv/bin/python -m app.goldapple.probe diag
```

Показывает, отдаёт ли ЗЯ карточку, и если нет — что именно мешает. Снять сырой
ответ (пригодится, если ЗЯ снова поменяет формат):


```
    url.py             разбор ссылок → itemId
    fingerprint.py     согласованный отпечаток браузера
    fetcher.py         HTTP-клиент, пул прокси, детекция антибота
    session.py         браузерная сессия (режим без прокси)
    browser.py         разовое прохождение device-check
    parser.py          нормализация ответа карточки
    client.py          фасад
    probe.py           CLI-диагностика
  services/
```

### Модель данных

- `users` — пользователи Telegram
- `products` — товары, текущее состояние + сырой JSON ответа
- `price_points` — история; точка пишется **только при изменении**, иначе
  таблица растёт линейно по времени без всякой пользы
- `watches` — подписка «пользователь ↔ товар» с настройками и целевой ценой
- `events` — зафиксированные изменения, источник уведомлений и ленты в аппе

### Как работает опрос

`worker` раз в минуту берёт товары, у которых есть хотя бы одна подписка
и которые не проверялись дольше `CHECK_INTERVAL`. Между запросами — рваная
пауза около `CHECK_DELAY_BETWEEN`: ровный ритм подозрителен для антибота.
Товары со сбоями отодвигаются экспоненциальным откатом, чтобы мёртвая карточка
не съедала лимит запросов.

Уведомление отправляется, только если изменение реально произошло и
пользователь на него подписан. Заданная целевая цена главнее общей настройки:
сообщение придёт при достижении отметки, а не при любом снижении. Событие
«товар закончился» пишется в историю, но в уведомления не выносится — это шум.

## Развёртывание

Развёрнуто на `box.botiq.cc` по конвенциям сервера (venv + systemd + nginx +
certbot, без Docker).

| Что | Где |
|---|---|
| Код | `/home/admin/applespy` |
| Статика мини-аппа | `/var/www/applespy.panoff.dev` |
| Конфигурация | `/home/admin/applespy/.env` (режим 600) |
| nginx | `/etc/nginx/sites-available/applespy.panoff.dev` |
| Сервисы | `applespy-web` (uvicorn, 127.0.0.1:8020), `applespy-bot`, `applespy-worker` |
| БД | PostgreSQL, роль и база `applespy` |
| Сертификат | Let's Encrypt, автопродление настроено certbot |

**Про память — это здесь узкое место.** Сервер делит 3,5 ГБ с Mail-in-a-Box,
свободно обычно 300–400 МБ, а Chromium просит около 350 МБ. Меры:

- `MemoryMax=800M` на `applespy-web` и `applespy-worker` — жёсткий предохранитель,
  чтобы браузер не мог уронить почту;
- **файловый замок `/tmp/applespy-browser.lock`** — на машине живёт только один
  Chromium. Браузер поднимают оба процесса (веб — по кнопкам «добавить»
  и «обновить», воркер — по расписанию), и два одновременных съели бы ~700 МБ,
  которых нет;
- фоновый сторож закрывает браузер после 3 минут простоя. Проверять простой
  только при следующем запросе недостаточно: без сторожа Chromium висел бы
  до самого перезапуска сервиса;
- у самого Chromium отключены изоляция сайтов и GPU, ограничены рендереры
  и куча JS.

Если понадобится снять эти ограничения — самый простой путь не «дать больше
памяти», а перейти на резидентные РФ-прокси: тогда регулярный опрос идёт через
httpx, а браузер нужен раз в час на несколько секунд.

### Обновление

```bash
bash deploy/update.sh
```

Собирает фронтенд, заливает код, накатывает миграции и перезапускает сервисы.
`.env` и `venv` на сервере не трогаются.

### Логи

```bash
sudo journalctl -u applespy-worker -f
```

## Настройки `.env`

| Переменная | Смысл |
|---|---|
| `BOT_TOKEN` | токен бота |
| `WEBAPP_URL` | публичный https-адрес мини-аппа |
| `BOT_MODE` | `polling` (по умолчанию) или `webhook` |
| `GA_CITY_ID` | ФИАС-код города — от него зависят цена и наличие |
| `GA_REGION_ID` | ФИАС-код региона; если пусто, берётся город. Для Тюмени **обязателен** |
| `GA_PROXIES` | пул прокси через запятую; пусто = режим браузерной сессии |
| `GA_BROWSER_FALLBACK` | должен быть `true`: без браузера device-check не пройти |
| `GA_COOKIE_TTL` | время жизни клиренса, секунды |
| `CHECK_INTERVAL` | как часто проверять один товар, секунды |
| `CHECK_DELAY_BETWEEN` | пауза между запросами внутри цикла |
| `CHECK_BATCH_SIZE` | максимум товаров за цикл |
| `STOCK_CONFIRMATIONS` | сколько совпадений подряд нужно, чтобы поверить в смену наличия (по умолчанию 2) |
| `NOTIFY_COOLDOWN` | минимальный интервал между одинаковыми уведомлениями по товару, секунды |
| `ADMIN_IDS` | telegram id админов; **пустое значение = `/diag` закрыт для всех** |

## Что стоит иметь в виду дальше

- **Формат ответа ЗЯ меняется.** Парсер защитный (сначала известные пути,
  потом рекурсивный поиск), сырой JSON всегда сохраняется в `products.raw`,
  так что данные не теряются. При поломке — `probe card --raw` и правка
  `parser.py`.
- **Успешность без прокси ~85–90%.** Промах не страшен: следующий цикл через
  15 минут повторит. Если понадобится стабильнее и быстрее — резидентные РФ
  прокси переводят систему на httpx-путь.
- **Города.** Сейчас мониторинг ведётся по **Тюмени**. Наличие сильно
  отличается от города к городу, поэтому пара GUID задаётся в `.env`:

  | Город | `GA_CITY_ID` | `GA_REGION_ID` |
  |---|---|---|
  | Тюмень | `9ae64229-9f7b-4149-b27a-d1f6ec74b5ce` | `54049357-326d-4b8f-b224-3c6dc25d6dd3` |
  | Москва | `0c5b2444-70a0-4932-980c-b4dc0d3f02b5` | тот же, что город |

  GUID нового города проверяется так: поднять сессию и вызвать
  `POST /front/api/location/address` с `{"addressId": "<GUID>"}` — в ответе
  придут `city` и `regionId`. После проверки сессию надо пересоздать, этот
  вызов сбрасывает клиренс.

  Сейчас город общий для всех пользователей. Если понадобится у каждого свой,
  это поле в `watches` плюс отдельная сессия на город — заметная переделка,
  потому что сессия браузера одна на процесс.
